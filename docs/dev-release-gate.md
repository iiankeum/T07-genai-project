# dev 배포 전 확인

`dev` 머지는 약 1분 안에 서버 배포를 시작한다. 새 워크플로우는 **검사만** 하며 자동 머지·서버 접속·배포를 하지 않는다. GitHub 필수 검사 설정을 대신하지도 않는다.

## CI가 확인하는 것

- Node 24와 실제 배포와 같은 `npm ci --omit=dev --ignore-scripts` 설치.
- 별도 구 dev 체크아웃으로 가짜 DB 생성 → 후보 버전 → 구버전 DB 모듈 → 후보 버전으로 재개방. 통화·카드·용어·메타 값, 새 카드 컬럼 기본값, SQLite 무결성과 쓰기 보존.
- 임시 자료 폴더·AI off·빈 키·200MB Node heap으로 저장소 루트에서 실제 서버 엔트리 실행.
- 비공개 모드의 업무 API 401, 공개 데모 모드 200, 정적 화면 및 health의 실제 후보 SHA 일치.
- 별도 기존 회귀의 전체 디렉터리 백업 복원·가짜 업로드/일꾼/API·비용 차단.
- dev 대상 PR은 정확한 base SHA를 사용한다. 통합 브랜치 대상 검사는 당시 dev SHA를 별도 체크아웃하고 후보/기준 SHA를 결과에 기록한다.

기존 App checks와 secret-scan도 모두 통과해야 한다. 후보나 dev가 바뀌면 새 merge 결과를 다시 검사한다. 테스트는 운영 자료를 읽지 않는다.

## CI로 확인하지 못하는 것

- 실제 서버 자료의 최신 백업, 관리자 복구 권한, 설치된 root 소유 배포 스크립트와 기록용 사본의 일치.
- 실제 env·메일 발송·일꾼·AI 품질·신규 계정 사용 가능 여부.
- 300MB cgroup 아래 장시간 부하. 200MB Node heap 설정은 이 검사를 대신하지 않는다.
- 구버전 서버의 모든 API 재실행. 검증한 것은 구버전 DB 모듈 재개방·읽기/쓰기다.

## 운영 자료 확인이 선행돼야 하는 이유

배포 장치의 자동 롤백은 코드 링크만 되돌리고 DB를 복원하지 않는다. 새 버전은 계정/워크스페이스 DB를 사용한다. 기존 단일 DB는 보존돼도 기본 데모 화면에서는 안 보일 수 있다. 실제 기존 업무 연결에는 legacy owner 설정·인증 검토가 필요하다. 계정 메일은 outbox 방식이며 자동 외부 이메일 발송이 아니다. AI 기본값은 off다.

따라서 CI 통과만으로 실서버 전환 준비 완료라 하지 않는다. 실제 자료·백업 확인이 안 되면 dev 머지를 멈춘다. 비밀값을 채팅·공개 PR·로그에 붙이지 않는다.

## 머지 뒤 확인

허용된 검증이 끝나면 정확한 PR head로 일반 merge한다(force 금지). `/_deploy/status.json`의 live.commit과 last.result, `/healthz`의 commit이 실제 dev SHA와 일치하는지 확인한다. 실패/rollback이면 성공이라고 보고하지 않는다. 자료 변경이 필요한 복구는 관리자와 별도 확인한다.
