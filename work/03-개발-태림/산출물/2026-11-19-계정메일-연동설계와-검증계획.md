# 계정 메일: 공급자 선정 전 안전한 연동 설계

**설계안이며 아직 구현하지 않았다. 공급자·발신 도메인·자격증명 선택, 실메일 발송, 운영 서버 변경, GitHub 쓰기 재시도는 하지 않는다.** 기준은 integration `0f259ea`의 계정 코드와 로컬 감사 커밋 `fb50419`다.

> 후속: 아래는 설계 당시 기록이다. 공급자 없는 단일 시도 계약만 별도로 구현·검증했다. [최소 구현 범위](2026-11-19-계정메일-전송경계-최소구현.md). 큐/실발송/마이그레이션은 여전히 미구현이다.

## 1. 현재 코드에서 확인한 사실

- v1.6 AUTH01/03/05는 이메일 인증·비밀번호 복구·구성원 초대를 요구한다. [고정 개발요청서 2e498fc](https://github.com/iiankeum/T07-genai-project/blob/2e498fc785a4a94ae7077b39b5a60a71492886a8/work/01-기획-남희/산출물/기획서-v1.6/md/아맞다_02_개발요청서_v1.6.md)의 899–905행.
- `src/app/lib/auth.mjs:22,262–280`: 허용 메일 모드는 outbox뿐이다. 전달물 JSON에는 수신 주소와 인증 URL이 들어가며 디렉터리0700/파일0600으로 작성한다. 외부 발송이 아니다.
- `auth.mjs:63–89,275–293`: account_links에는 토큰 해시, 종류, 이메일, 공간, 역할, 만료, 사용시각이 저장된다. 동기 `BEGIN IMMEDIATE` 트랜잭션 안에서 기존 링크 무효화→새 링크 삽입→outbox 파일 쓰기를 수행한다.
- 토큰 TTL은 인증24시간/재설정30분/초대7일이다. 사용·만료·재발송으로 무효화한다. 인증/재설정 성공 시 기존 세션도 지운다 (`auth.mjs:275–293,372–402`).
- 가입/재설정 요청은 존재 여부에 관계없이 `{ok:true}`를 돌려주도록 작성됐다. 하지만 비동기 전송을 추가한 후에도 응답 시간까지 충분히 균일한지는 별도 검증해야 한다.
- `routes/auth.mjs:16–25,74–86`: IP 및 경로별 빈도 제한이 있다. 수신 주소별 지속 제한이나 실제 발송 예산은 아직 메일 전용 설계가 아니다.
- `test/auth.test.mjs`는 임시 outbox에서 토큰을 읽어 약관·일회 사용·초대 취소/재전송·세션·역할을 검증한다. 이것은 실제 수신 검증이 아니다.

## 2. 하지 말아야 할 단순 치환

`writeOutbox()`를 SMTP/HTTP 호출로 바꾸고 `await`만 추가하면 안 된다. 현재 트랜잭션 함수는 동기이며 Promise를 기다리지 않는다. DB lock을 잡은 채 네트워크를 기다리거나, 메일만 발송되고 DB가 롤백되는 불일치가 생길 수 있다.

현재 파일 outbox와 DB도 서로 다른 저장소라 원자적 커밋이 아니다. 이 구조를 실발송 큐처럼 재사용하거나 기존 폴더의 JSON을 일괄 발송해서는 안 된다. 과거·취소·만료·테스트 링크가 섞일 수 있다.

## 3. 권장 구조: 계정 트랜잭션과 발송 분리

```text
가입/재설정/초대 요청
  → 기존 검증·권한·동의·요청 제한
  → 하나의 계정 DB 트랜잭션
       기존 링크 무효화 + 새 account_link + delivery_job 생성
  → COMMIT → 일반적인 요청 접수 응답

별도 발송 루프
  → 유효한 pending job을 lease로 확보
  → 만료/취소/이미사용 여부 재확인
  → 선택된 adapter로 전송 (DB transaction 밖)
  → accepted / retry / failed 등 결과만 기록
```

- 현 `outbox` 모드는 Mac 개발용 로컬 인증과 기존 테스트 호환성을 위해 유지한다. 새 외부 모드는 명시적으로 선택한 경우에만 켠다. 설정이 불완전하면 fail closed하며 outbox로 몰래 전환하지 않는다.
- 공급자 중립 `MailTransport.send(message, {idempotencyKey, signal})` 계약부터 만든다. 운영 adapter는 아직 구현/선정하지 않는다. 테스트 adapter는 메모리에만 기록하고 네트워크를 사용할 수 없다.
- 메시지는 코드가 생성한 verify/reset/invite 고정 템플릿만 허용한다. 요청 본문이 endpoint·from·subject·임의 HTML·첨부·추적 URL을 지정하지 못하게 한다. 이름/공간 이름은 escaping, 메일 헤더는 CR/LF 거절.
- `mail_delivery_jobs`를 계정 DB에 additive migration으로 추가한다. `id`, `account_link_id`, `status`, `attempts`, `next_attempt_at`, `lease_token`, `lease_until`, `created_at`, `expires_at`, 제한된 오류 분류를 둔다. 링크와 작업 생성·이전 작업 취소를 같은 트랜잭션으로 묶는다.
- 수신 주소·원문 URL이 필요한 큐 payload는 인증된 암호화로 보관한다. 토큰 해시는 기존처럼 별도 유지한다. AEAD·고유 nonce·key ID를 사용하고 AAD에 job/link ID·종류·대상을 바인딩한다. 기존 account_links.email 등 계정 PII까지 암호화되는 것은 아니며 전체 DB 암호화라고 부르지 않는다. 암호화 키의 보관·복구·회전 정책은 운영자 선택 전 확정하지 않는다. 키를 코드/DB와 함께 커밋하거나 로그에 남기지 않는다. 필요한 키가 없으면 외부 모드를 시작하지 않는다.
- 커밋 직후 알림만 믿지 말고 재시작 후 지속적으로 큐를 조회한다. 여러 프로세스는 짧은 트랜잭션으로 하나의 job을 claim한다. lease 소유자가 아닌 늦은 응답은 결과를 덮지 못한다. DB 트랜잭션 중 네트워크를 호출하지 않는다.
- 동일 job 재시도는 같은 메시지·링크·idempotency key를 사용한다. timeout은 실제 수락 여부가 불명확할 수 있다. **메일 exactly-once를 보장하지 않는다.** 공급자 중복 방지가 없거나 수락 후 프로세스가 죽으면 중복 메일이 가능하다. 동일 링크는 일회용이며 새 토큰을 재시도마다 만들지 않는다.
- 명시적 재발송만 기존 정책대로 새 링크를 발급하고 이전 링크/미발송 job을 취소한다. 전송 직전 취소 검사는 하지만 이미 전송 중인 메일을 회수할 수는 없다. 늦게 도착한 취소 링크는 서버가 거절해야 한다.
- 만료·사용·취소 또는 작업공간이 삭제된 job은 보내지 않고 종료한다. 성공 수락/취소/만료 후 민감 payload를 제거하고 최소 상태 메타데이터만 정해진 기간 보관한다. `accepted`는 공급자 접수이지 수신함 도착이 아니다.

## 4. 보안·사용자 표시

- 외부 모드는 운영자가 고정한 HTTPS 기본 origin으로만 링크를 만든다. 사용자 Host/Forwarded 헤더를 링크 생성에 쓰지 않는다. 자격정보·query·fragment·임의 path가 붙은 기본 주소를 거절한다. 로컬 outbox의 loopback 주소는 별도 모드로 남긴다.
- 존재/미존재 계정의 요청 응답·문구를 같게 유지하고 발송을 비동기로 분리한다. 비밀번호 재설정 요청만으로 계정을 잠그지 않는다. 주소별 HMAC 키 기반 cooldown/일일 quota와 전역 발송 상한을 DB에 둬 재시작·다중 인스턴스로 우회되지 않게 한다. 키/제한값은 운영 정책으로 결정한다.
- 링크 GET과 메일 보안 스캐너 접근만으로 계정 상태를 바꾸지 않는다. 현재의 명시적 POST와 토큰 검증을 유지한다. reset/verify 화면은 no-referrer와 토큰 URL 정리, 제3자 자원 부재를 별도로 검증한다.
- 공급자 응답·예외 전문을 사용자/로그에 내보내지 않는다. 이메일·원문 URL·토큰·API 키 없는 오류 코드와 job 상태 집계만 남긴다.
- 관리자 진단도 전체 사용자/공간 메일을 일반 workspace 관리자에게 노출하지 않는다. 공개 API는 토큰·URL·큐 payload를 반환하지 않는다. 재설정 요청에 발송 여부를 공개해서 계정 존재를 알려주지 않는다.
- 화면은 “요청을 접수했습니다”와 “메일 발송/수신 완료”를 구분한다. outbox에서는 개발용 로컬 링크임을 명확히 한다. 외부 메일 장애가 수동 주문·이미 로그인한 사용자의 업무 전체를 막지 않아야 한다.

OWASP는 복구 요청의 동일 응답·시간 특성, 암호학적 난수/일회용/만료 토큰, 과도한 요청 방어와 안전한 링크 처리를 권고한다. 여기의 큐·lease·암호화 구현은 그 문서의 필수 구현이라고 주장하지 않고 이 코드의 트랜잭션 구조에 맞춘 설계 제안이다. [OWASP Forgot Password Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## 5. 공급자 없이 먼저 할 수 있는 PR 순서

1. **경계 분리:** 고정 템플릿/transport 계약·fake adapter, 기존 outbox 회귀 보존. 운영 모드 기본값은 바꾸지 않는다.
2. **원자적 큐:** additive schema·링크+job 트랜잭션·민감 payload 암호화 경계·복원/마이그레이션 시험. 네트워크 adapter 없음.
3. **내구성:** fake transport로 lease·timeout·재시작·취소·재발송·quota·최소 관측 검증. 발송 루프는 명시 활성화 전 실행되지 않는다.
4. **공급자 선택 후:** 승인된 adapter·TLS·자격증명·발신 인증·운영 정책 구현. 승인된 시험 수신자에게만 실제 end-to-end 수행.
5. **출시 게이트:** 실제 인증/복구/초대 수신·클릭·만료·차단·모바일 흐름과 백업복원 확인 후 readiness 상태 갱신. 코드만 추가했다고 “메일 준비 완료”로 바꾸지 않는다.

현재 계획 PR은 1~3을 자동 실행하도록 승인한 것이 아니다. 후속 구현 범위는 별도 작업에서 정한다.

## 7. 실제 발송 전 운영자 결정 목록

- 발신 도메인·주소·공급자/전송 방식, 비용·사용량 상한과 담당자
- 자격증명과 큐 암호화/HMAC 키의 보관·회전·복구 권한
- 도메인 발신 인증, TLS, 반송/민원 처리와 보관·국외이전 고지
- 승인된 시험 수신자, 실제 수신함/스팸함 확인, 장애 대응 기준

이는 지금 사용자에게 자격증명을 달라는 요청이 아니다. 구현과 발송을 분리하기 위한 미결 목록이다. 공급자 선정을 대신하거나 실메일을 보내지 않았다.
