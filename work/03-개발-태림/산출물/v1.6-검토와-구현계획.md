## 크리티컬 패스

1. **데이터 계약과 비용 차단**: 원본 통화·문장 시각·카드·근거·사람의 검토 상태를 유지한다. 유료 호출은 기본 차단하고 fixture를 명시한다.
2. **인증과 작업공간 격리**: 로그인, 4개 역할, 워크스페이스별 DB·음성 저장 경계를 먼저 정한다. 작업공간마다 데이터를 찾는 서버 경로가 일치해야 한다.
3. **주문 처리의 일관성**: 필수값과 불확실 항목 확인 → 확정 잠금 → 출고 → 명시적 되돌리기를 검증한다. 재연락은 독립 속성이다.
4. **지식·질의 연결**: 승인본과 수정안을 분리한다. 승인된 지식과 선택된 작업공간의 실제 통화만 질문의 근거로 사용한다.
5. **화면 통합**: 통화 목록·문장·주문 카드의 연결, 근거 이동, 저장 상태, 모바일 메뉴와 키보드 사용성을 맞춘다.
6. **검증과 제출**: 실제 서버 API 회귀 테스트 → 브라우저 E2E → 화면 캡처 → 요구사항별 잔여사항 → 작업 일지와 PR 순으로 제출한다.

자체 서버 설치와 업종별 설정 문서는 2~5와 병렬로 작성하되 최종 API와 설정값으로 설치 검증한다. 화면 개발은 2~4의 계약에 의존한다. 따라서 화면 캡처가 먼저 있어도 전체 완료를 뜻하지 않는다.

## 오픈소스 확장 경계

공통 계층은 사용자·권한·작업공간, 녹음 수집, 근거 문장, 상태 이력, 승인형 지식, 제공자 호출 제한과 화면 토큰이다. 업종 계층은 개념 정의, 필드 라벨, 필수값, 검증, 상태 전이 조건과 추출 지침이다. 설치 계층은 저장소, TLS, 메일, 음성 워커, AI 키와 백업이다.

온톨로지는 이름만 바꾸는 테마가 아니다. 같은 개념의 별칭, 개념 간 관계, 출처와 승인 버전까지 함께 관리한다. 예를 들어 ‘미미’와 ‘엔진 마운트’의 관계가 승인되면 다음 요청의 힌트로 사용할 수 있지만 품번·재고·호환성을 새로 만들어 내는 근거가 되지는 않는다.

## 검증 원칙

- 개발·회귀 테스트는 외부 유료 제공자를 차단하고 결정적인 fixture 또는 가짜 클라이언트를 사용한다.
- 코드 테스트, 서버 API E2E, 실제 브라우저 E2E, Docker 설치, 실제 GPU/유료 제공자 실증을 별도 결과로 보고한다.
- 화면 캡처에는 가짜 데이터만 사용한다. fixture 결과를 실제 AI 응답으로 표시하지 않는다.
- 실제 수행 결과와 잔여 요구사항은 후속 검증 보고서와 LOG.md에 기록한다. 이 문서는 완료 확인서가 아니다.
