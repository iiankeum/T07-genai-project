## 기획서 읽는 법

- **2쪽 한 장 요약**만 읽어도 문제 · 기능 10개 · 조사 결론 · 데모 범위가 나온다. 목차도 여기 있다.
- **기능 쪽(F01~F10)** 은 한 쪽에 한 기능이다: 왜 필요한가 → 언제 쓰나(장면 그림 · 장면 글) → 화면 흐름 → 완료 기준(눈으로 확인) → 조사에서 본 것.
- 기능 ID(F01~F15)는 개발 쪽 설계 문서(dev 가지 `src/app/docs/설계.md`)와 구현-대조표에서 같은 번호를 쓴다.
- 근거 표시: [확인] 공식 자료 · [기사] · [후기] · [현장 문서](비공개 업무 프로그램 문서를 일반화) · [추정].

## 사고 과정 요약

1. **먼저 만들 수 있는 것부터** — 아침 결과물이 「기획서의 기능이 모두 동작하는 사이트」라서, 조사를 띄우자마자 지금 조건(1GB 서버 · Claude API · PC Whisper 일꾼 · 브라우저)으로 만들 수 있는 기능만 골라 기능목록 v0 를 넘겼다(시작 후 약 5분). 전화기 연동 · 카탈로그 · 대리점 전산 연동은 처음부터 「다음 단계」로 뺐다.
2. **뼈대는 회의록, 살은 프로토타입** — 킥오프의 목표 경험(실시간 받아쓰기 · 색 표시와 주문 카드 · 용어집 · 대시보드 · 할 일 추천 · 지난 기록 질문)을 기능의 뼈대로 삼고, 팀 프로토타입 셋에서 이미 검증된 원칙(「AI 는 초안, 품번은 사람」 · 확정 조건 · 「들어 보기」 · 원문 대조)을 붙였다.
3. **조사는 넓게, 주장은 좁게** — 서비스 60여 개 · 출처 약 330개를 봤다. 반박 검증에서 고쳐진 것(대리점 수 · 교육 표의 짝 · AI 오더 「방침」 · 「주요 방법 중 하나」)을 기획서 문장에 그대로 반영했다. 「칸마다 근거를 붙이는 곳이 없다」는 해외 조사(Gong · Plaud · Outreach 의 근거 표시)를 보고 「전화 주문 카드의 칸마다 근거와 재생 위치를 붙이는 곳은 찾지 못했다」로 좁혔다.
4. **차별점은 받아쓰기가 아니다** — 받아쓰기 · 요약은 휴대폰 · 통신사 앱이 무료로 준다. 우리 자리는 ① 전화 주문 전용 카드 ② 칸마다 근거 · 「들어 보기」 ③ 대표 유선전화의 녹음 파일 ④ 현장 말 · 거래처 사전 ⑤ 부장님이 쓰는 화면 ⑥ 소리는 PC 안에서.
5. **업계의 칸 채우기 규칙을 가져옴** — 칸 수 고정 · 사람 승인 · 값마다 근거 · 기존 칸에만 · 덮어쓰기 규칙(사람이 고친 칸은 AI 가 덮어쓰지 않음). 마지막 것은 개발 방에 따로 알렸다.
6. **그림은 캐릭터 시트 먼저** — 같은 인물이 모든 장면에서 같게 보이도록 시트를 먼저 그리고 장면마다 참고로 넣었다(대표님 지난 영상 작업의 방식). 그림에는 글자 · 로고를 넣지 않고 글은 HTML 로 얹었다.
7. **공개 저장소 거르기** — 대리점 업무 프로그램(비공개)에서 읽은 것은 업계 일반 흐름만 남기고, 그 제품만의 기능 · 화면 · 용어 · 이름은 뺐다. 대리점 이름이 드러나는 출처 주소도 뺐다.

## 확인 못 한 사실 (현장 · 팀 확인 필요)

- 국내 대리점의 주문 채널별 비율(전화 · 문자 사진 · 카톡 · 팩스) — 통계를 찾지 못했다
- 하루 주문 전화 수 · 몰리는 시간 · 놓친 전화 비율 · 「두 개라 했다」 다툼 빈도
- 본사 입고 횟수 · 주문 마감 시각 · 자체 배송 회차 · 외상 마감일 · 세금계산서 주기
- 접수 담당의 나이대, 현장 호칭 「부장님」 = 보고서의 「프론트 부장」인지
- 현장 녹음 파일에 걸려 온 번호 · 수신/발신이 남는지, 양쪽 목소리가 한 채널인지
- 본사의 「AI 를 활용한 오더 시스템」 방침(2025-06)의 실제 내용
- 각 서비스의 일부 기능 · 값(비교표의 「?」) — 조사 도중 웹 검색 한도가 다 차서 못 찾은 것 포함
